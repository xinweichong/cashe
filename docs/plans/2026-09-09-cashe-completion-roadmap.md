# Cashe completion roadmap — 2026-09-09

Baseline: `f409441`. Read with the [implementation audit](2026-09-09-cashe-next-level-audit.md) and [original product plan](2026-09-05-cashe-next-level-plan.md). This is a proposed execution plan, not a record of completed implementation or an authorization to deploy.

## Delivery decision

Keep the existing monolith, SQLite/WAL, per-user databases, source-event/outbox foundation, and React web client. Finish the web release before native distribution. Keep the new experience opt-in until financial parity, privacy, navigation, and device gates pass.

The next increment should **not** simply be another recurring feature. Fix the audited cache, route, and AI-policy gaps first. Then establish canonical money and command contracts, so imports, splits, forecasts, and offline entry share dependable primitives.

Operational validation starts immediately alongside code work. It cannot be deferred to the final deployment day. AI enrichment can remain disabled throughout core product development; deterministic functionality is the release fallback.

## R03 — Finish shared transaction commands and v2 Transaction

**Implementation**

- Build on `transaction_validation.py`, `Storage.create_manual_transaction`, existing request receipts, and the ingestion outbox. Extract shared orchestration only where multiple real callers need it; keep parser-specific receipt handling separate.
- Define typed v2 `Transaction` and create/correct/delete results containing classification, canonical Money, conversion/provenance summaries, revision, and optional relation IDs. Exclude raw payloads, credentials, internal source IDs and arbitrary DB columns.
- Generate TypeScript contracts from the v2 API schema and check for contract drift in CI; migrate callers incrementally while keeping v1 compatibility explicit.
- Add revision numbers, retained deletion records, and mutation history sufficient for safe undo. Updates accept an expected revision and return 409 with a safe current-state summary on conflict. A retry key binds to the accepted command fields; replay after deletion must not recreate it.
- Route web, direct Telegram, confirmed NL, later imports/OCR/offline drafts through the same monetary validation and mutation transaction. Preserve existing source identity conventions and capture-time trip behavior.
- Specify invalidation/recomputation for corrections, split/refund changes, trip membership, recurring links, reports and evidence. Capture metadata remains original evidence, not edited transaction truth.

**Exit checks**

Concurrent correction conflict, same-key/different-payload conflict, crash/replay, atomic remember-rule updates, undo after an intervening edit, deletion/replay, and identical accepted values across clients. Add auth/privacy tests for each new route and compatibility tests for callers still using v1.

**Status (2026-09-09): revisions, mutation/deletion history, the full typed v2 command surface (create/correct/delete/undo/restore), generated TypeScript contracts with a CI drift gate, a shared command module used by both the v2 HTTP API and Telegram, and the frontend's transaction CRUD are all done. Remaining: NL-confirmation/import/OCR routing, and R04's broader consumer migration.**

Done: migration 13 (`transactions.revision`, `transaction_mutations`, `deleted_transactions`); `Storage.update_transaction` accepts `expected_revision` and raises `RevisionConflict` (carrying the current row) on mismatch, records changed-field mutation history, and recomputes canonical money on any amount/currency/exchange_rate correction so those columns can't go stale; `Storage.delete_transaction` retains a snapshot before removing the row, never reused under the same id, and now returns the retained `deleted_at` timestamp; `PUT /api/v2/transactions/{id}` (`TransactionV2`/`TransactionCorrection` in `contracts.py`) returns classification, canonical Money, conversion provenance, and revision, with a 409 + current-state summary on a stale `expected_revision`. v1 `PUT /api/transactions/{id}` is untouched and still last-write-wins for existing callers — this was a deliberate compatibility choice, not an oversight.

`POST /api/v2/transactions` (`TransactionCreate`) and `DELETE /api/v2/transactions/{id}` (`TransactionDeletion`) now round out the typed command surface: create returns the same canonical-money/revision `TransactionV2` shape as correct/update (reusing `create_web_transaction`'s existing `Idempotency-Key` replay behavior), and delete returns the pre-deletion snapshot plus `deleted_at` instead of a bare status. Both are auth-scoped like the existing PUT route. v1 `POST`/`DELETE /api/transactions` are untouched.

`POST /api/v2/transactions/{id}/undo` (`TransactionUndo`) reads `transaction_mutations` back: it reverts a transaction to its state before its most recent recorded correction (the mutation whose `revision_after` equals the transaction's current revision), applying the stored `old` values including the canonical-money columns when amount/currency/exchange_rate changed. It always targets whichever correction most recently happened rather than a specific past edit, so an intervening edit changes what gets undone instead of blocking it; `expected_revision` lets a caller detect that and gets the same 409-with-current-state shape as PUT. The undo is itself appended as a new mutation with old/new swapped, keeping the log append-only — a second undo redoes the edit.

`Storage.restore_deleted_transaction` / `POST /api/v2/transactions/{id}/restore` restore a deleted transaction from its retained snapshot. This needed migration 14: `deleted_transactions` (migration 13) only ever retained enough for a conflict summary (amount/currency/merchant/category/transaction_date/type), not enough to recreate a row — migration 14 adds `description`, `exchange_rate`, and the canonical-money/conversion columns, and `delete_transaction` now stores all of them. Restore recreates the row under its original id with a bumped revision; refuses (with a distinguishing error) to restore a still-existing transaction or a pre-migration-14 snapshot.

`scripts/export_v2_openapi_schema.py` filters `app.openapi()` to `/api/v2/*` paths (plus transitively-referenced schemas) and `openapi-typescript` turns that into `src/web/frontend/src/api/v2-schema.gen.ts`. `npm run check-types:v2` regenerates and git-diffs both files; a new `contracts` CI job runs it, so a backend contract change unmatched by regenerated frontend types is a CI failure. openapi-typescript's published typescript peer (`^5.x`) lags this repo's `~6.0.2` — installed with `--force`, not `--legacy-peer-deps` (the latter silently dropped `@testing-library/dom` from the resolved tree).

`src/transaction_commands.py` is now the single place that turns a Storage mutation into a typed v2 result (`to_v2`, `create_manual`, `create_web`, `correct`, `delete`, `undo`, `restore`) — moved out of `app.py`'s route closures. `app.py`'s five v2 routes delegate to it. `telegram_bot.py`'s seven correction call sites, its delete callback, and its "no Telegram message identity" create fallback now go through the same module instead of calling `Storage.update_transaction`/`delete_transaction`/`create_manual_transaction` directly — same underlying semantics, so bot behavior is unchanged, but corrections/deletions from chat run through the same code path as the v2 HTTP API. `create_telegram_transaction` and `confirm_telegram_draft` (chat_id/message_id and NL-draft identity respectively) are untouched — they encode idempotency identity that doesn't map onto the web `Idempotency-Key` contract.

The frontend's `api.createTransaction`/`updateTransaction`/`deleteTransaction` now call the v2 endpoints, typed against the generated schema. This was safe to switch without a UI rewrite — `useCreateTransaction`/`useUpdateTransaction`/`useDeleteTransaction` never read the mutation response for cache display, only the request payload (optimistic patch) and a refetch of the untouched v1 GET routes — but surfaced a real gap: `TransactionCreate` had no `source` field, so switching would have silently turned every "Cash" entry into "manual"; added `source: Literal["manual", "cash"] = "manual"`. Verified end-to-end against a live backend + vite dev server via a scripted Playwright session (not just `tsc`/unit tests, which mock the hooks and wouldn't have caught the `source` gap): create, edit, and delete all confirmed hitting `/api/v2/transactions*` with correct results.

Remaining exit checks — same-key/different-payload conflict, deletion/replay against the retry-key idempotency table, atomic remember-rule updates under a revision conflict (not just a DB-trigger abort), and identical accepted values across clients (Telegram vs. web, given the same input) — are now covered by tests.

**Follow-up (not done):**
- Routing NL confirmation (`confirm_telegram_draft`) and future imports/OCR through the shared command path — distinct identity/idempotency mechanisms from what `transaction_commands` currently wraps; left untouched rather than forced into a shape that doesn't fit yet.
- Frontend: nothing else consumes the generated v2 types yet (only transaction create/update/delete); Activity list/detail views still render the v1 flat `Transaction` shape from GET responses, which is what R04/R09 will need to address alongside shared-facts consumers generally.

Done: `spending_facts._rows()`/`_resolve_money`, every money aggregate in `analytics.py`, and every money query in `storage.py` (`get_spending_summary`, `get_income_summary`, `get_balance`, `get_merchant_ranking`, `get_average_daily`, `get_trend`, `get_trend_by_category`, `get_merchant_trend`, `get_merchant_list`, `get_merchant_profile`, `get_budget_progress`, `get_savings_overview`, `get_health_score`, `get_trip_summary`, `_get_subscription_last_amount`, plus `user_manager.py`'s scheduled LLM-insight generation) now read the `reporting_minor_units`/`conversion_status` Storage already computes at write time (R02's `canonical_money.py`) instead of recomputing `amount * exchange_rate` on every read. This also surfaced and fixed real NULL-handling gaps the old always-non-NULL expression never had to consider: `get_trip_summary`'s Python-side `sum()`/`round()` over per-row amounts, and `get_health_score`'s anomaly detection comparing a possibly-`None` transaction amount against a possibly-`None` all-unresolved merchant average — both now correctly exclude unresolved transactions instead of crashing.

`money_basis` renamed from `"legacy_values_rounded_per_transaction"` to `"canonical_minor_units_with_legacy_fallback"` to describe what it now actually does (nothing pinned the old literal). `get_goal_progress`'s average-contribution-as-monthly-rate formula was left untouched — it's explicitly R13 scope (dated contributions over elapsed windows), and doesn't touch the `transactions` table's currency/FX columns at all (`goal_contributions.amount` is SGD-only by design).

## Possible follow-ups (not scheduled)

**Unify `analytics.py`/`spending_facts.py` period semantics.** Deliberately not attempted as part of R04, and not required by R04's exit checks — the roadmap explicitly permits "intentional compatibility changes" over forced parity, and both `test_current_month_total_agrees_but_previous_period_intentionally_diverges` and the earlier R02/R03/R04 status notes already record why the two modules disagree rather than treating it as an oversight. Flagged here as the concrete option-3 path if the divergence is ever worth closing:

- `analytics.py` (serves Explore's period comparisons) computes "previous period" as a pure equal-elapsed-days lookback from the current period's start, ignoring calendar-month boundaries. `spending_facts.py` (serves Home/Telegram/Activity) anchors "previous" to the actual previous calendar month, clipped to the shorter of the two months' day counts. Confirmed via `tests/test_r04_exit_check_parity.py`: a Jan 30 purchase counts toward Explore's previous-period total for an as-of-March-31 comparison but not Home's.
- Separately, `analytics._query_total` buckets transactions by the raw SQL `DATE(transaction_date)`, while `spending_facts._rows` projects timestamps into the configured local timezone before bucketing by day. A transaction timestamped near midnight UTC with a real timezone offset can land in different calendar-day buckets on each side — confirmed via direct repro (a transaction at `2026-04-10T23:30:00+00:00` lands in Home's Apr-11 SGT bucket but Explore's Apr-10 UTC-date bucket).
- Unifying these means deciding which semantics is authoritative (or introducing a third, shared primitive) and updating whichever consumer changes — Home's "day-over-day comparison" job and Explore's "calendar-range browsing" job may still warrant genuinely different current-period windows even after unification, so this isn't necessarily a single "pick one" fix. Architecturally riskier than anything else in R04: touches the comparison logic behind Explore's headline numbers and Home's driver/comparison surfaces simultaneously. Think carefully before starting, and don't attempt it inside an otherwise-unrelated increment.
